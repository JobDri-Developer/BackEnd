## 요약

- worker를 중지한 접수 경로는 1 RPS 10분, 10 RPS 10분, 30 RPS 2분에서 HTTP/acceptance 오류 없이 모두 기준을 통과했다.
- 30 RPS burst의 접수 p99는 55.34 ms였고, 3,601개 task와 queue message가 건수 기준으로 모두 보존됐다.
- 300건 backlog에서는 concurrency 10/25/50의 처리량 중앙값 차이가 작았지만 concurrency가 높을수록 completion p95가 증가했다.
- 1,000건 backlog에서는 concurrency 50에서 DB pending 최대 25가 관측됐고, concurrency 10보다 처리량 중앙값이 약 25.4% 낮았다. 로컬 기본 concurrency/prefetch는 10을 유지한다.
- 외부 API 지연, 429, 500/502/503, timeout, validation 실패, 중복 delivery, consumer restart, recovery spool replay에서 결과·Credit·DLQ 불변식을 확인했다.

## 병목과 결정

- 최초로 명확히 관측된 병목은 1,000건, concurrency 50에서의 DB connection wait다. DB pending 최대 25와 함께 처리량 감소 및 completion p95 증가가 관측됐다.
- 로컬 기본 worker concurrency/prefetch는 10을 유지한다. concurrency 25/50 상향은 운영 유사 DB pool과 실제 외부 API rate limit을 포함한 반복 측정 후 결정한다.
- concurrency 200은 50에서 안정성과 이득이 확인된 경우에만 수행한다는 조건을 충족하지 않아 실행하지 않았다.
- 30 RPS 접수는 기준을 통과했지만 실제 운영 부하 한계나 최대 처리 용량을 의미하지 않는다.
- RabbitMQ queue와 DLQ, worker, Credit, 외부 AI, Hikari 지표는 로컬 Grafana 대시보드와 Prometheus alert 규칙에 연결돼 있다. 운영 Grafana Cloud alert는 생성하거나 변경하지 않았다.

## 남은 한계

- 실제 OpenAI·Cohere rate limit과 latency는 비용·안전 제한 때문에 측정하지 않았다.
- RabbitMQ/PostgreSQL Testcontainers 테스트는 아직 없으며 broker restart와 실제 DLQ는 격리 compose E2E로 검증했다.
- 운영과 동일한 호스트 크기, 네트워크, DB pool에서 재검증하지 않았으므로 로컬 처리량을 운영 용량으로 환산하면 안 된다.
- 운영 Grafana Cloud 대시보드와 alert의 실제 배포·알림 전달은 이 작업 범위에 포함하지 않았다.
